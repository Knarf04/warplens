side by hand: compiled CUDA programs, Triton, and a first look at the CuTe DSL.

## `warplens run` for compiled programs

A program built by `nvcc` normally contains machine code for a real GPU and
links the CUDA runtime statically. Two things have to change, both at build
time and neither in the source:

```
nvcc -gencode arch=compute_100a,code=compute_100a --no-compress --cudart shared prog.cu -o prog
```

- `code=compute_100a` embeds PTX instead of machine code; `--no-compress`
  keeps it readable.
- `--cudart shared` links `libcudart.so`, which `warplens run` replaces.

`warplens run prog` starts the program with two small shim libraries
preloaded (`warplens/shim/`, C, built on first use against the installed CUDA
headers). They implement the runtime calls programs make and forward each one
over a socket to the `warplens run` process, which executes it in the
simulator:

| What the program does | What happens |
| --- | --- |
| registers its fat binary and kernels (compiler-generated) | the PTX is extracted and parsed; parameter sizes are read from it |
| `cudaMalloc`, `cudaMemcpy`, `cudaMemset`, `cudaFree` | simulated global memory; freed addresses are never reused |
| `kernel<<<grid, block, smem>>>(args)`, `cudaLaunchKernelExC` | a launch, with the cluster shape if one is given; argument bytes are copied as they are |
| `cudaGetDriverEntryPointByVersion("cuTensorMapEncodeTiled")`, then calling it | a warplens tensor map, validated like the real call |
| `printf` in a kernel | printed by the program, in order with its own output |
| device and function queries | a simulated B200: compute capability 10.0, 148 SMs |
| loads a module itself: `cuModuleLoadData`, `cudaLibraryLoadData`, then `cuModuleGetFunction` or `cudaLibraryGetKernel` | PTX text or a fat binary with PTX is parsed. Machine code is accepted only if the compiler kept the PTX (see the CuTe DSL below) |
| `cuLaunchKernel`, `cuLaunchKernelEx`, `cudaLaunchKernelExC` with such a kernel | a launch, as above |
| streams, events, `cudaMallocHost` | accepted; everything is synchronous and an elapsed time is zero |

An error in a kernel (a `MemoryFault`, a deadlock, unsupported PTX) is printed
and reaches the program as `cudaErrorLaunchFailure`, from the launch and from
the synchronize calls after it. A call to
`cudaGetLastError` clears the simulator's remembered kernel fault so another
experiment can run. This is a simulator recovery policy: real CUDA launch
failures may leave the process/context unusable, and clearing last-error state
does not repair that context.

A launch that is refused before the kernel runs is printed too and has the
code the CUDA runtime gives it:
`cudaErrorInvalidValue` for more shared memory than 227 KB per CTA or more
dynamic shared memory than the kernel was opted in to (below),
`cudaErrorInvalidConfiguration` for a block of more than 1024 threads or a
zero dimension, block dimensions above 1024 x 1024 x 64, or grid dimensions
above 2147483647 x 65535 x 65535, `cudaErrorInvalidClusterSize` for a cluster of
more than 16 CTAs or a grid that is not a whole number of clusters. Such an
error is returned by the launch call and once by `cudaGetLastError`;
`cudaDeviceSynchronize` does not repeat it. Through the driver API the first
two are `CUDA_ERROR_INVALID_VALUE` and the third is
`CUDA_ERROR_INVALID_CLUSTER_SIZE`. `cudaFuncSetAttribute` and
`cuFuncSetAttribute` accept a maximum dynamic shared-memory size of 0 to
227 KB less the kernel's static shared memory and a preferred carveout of -1
to 100, and return the invalid-value code for other values and for attributes
that can only be read; the cluster attributes (required shape, non-portable
sizes, scheduling policy) are accepted unchecked. The codes and where they
show up were measured on an RTX 3080 Ti at its own limits
(`validation/README.md`, "Launch errors"); that a B200 gives
`cudaErrorInvalidClusterSize` for the two cluster refusals is taken from the
meaning the CUDA headers give that code, not measured.

Like a GPU, the shim requires the shared-memory opt-in. A kernel may use
48 KB of shared memory, static plus dynamic; a launch with more dynamic
shared memory than that leaves is refused with `cudaErrorInvalidValue`
(`CUDA_ERROR_INVALID_VALUE`) unless the program first called
`cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, n)`
or `cuFuncSetAttribute(function, CU_FUNC_ATTRIBUTE_MAX_DYNAMIC_SHARED_SIZE_BYTES, n)`
with n at least the dynamic size of the launch. The message names the kernel,
what it asked for and what it may use. The attribute belongs to one kernel,
replaces the default (a smaller n lowers it), and is what
`cudaFuncGetAttributes` reports as `maxDynamicSharedSizeBytes`. A kernel
whose static shared memory alone is more than 48 KB needs no opt-in and may
use all the dynamic shared memory that is left of 227 KB. This is the rule an
RTX 3080 Ti follows at its own limits (`validation/README.md`, "The
shared-memory opt-in"; `default_max_dynamic` in `warplens/units/smem.py`);
that a B200 follows it is assumed until the rental (RT-15). `Device.launch`
of the Python API takes the shared memory of the launch and has no opt-in
step, and neither has the Triton driver, which launches through it (Triton's
own launcher sets the attribute on a GPU).

The shim libraries are built from `warplens/shim/` by `build.sh`, which
records next to them what they were built from (`warplens-shim.stamp`: a
digest of the C sources, `protocol.h` and `build.sh`, and one of the CUDA
headers). Every `warplens run` compares that with the sources it has, once,
before the program starts. A build made by hand in `warplens/shim/lib/` that
is of other sources is rebuilt in place, with a line that says so; if it
cannot be rebuilt (no compiler, no headers) the run stops with the reason
instead of loading it. Builds in the user cache are kept per source and
toolkit and checked the same way.

At exit `warplens run`
prints one line per kernel launch and any findings. `--timing` adds the
approximate timing model.

For the CUTLASS tutorials this replaces the hand-built arguments of
`examples/03_cutlass_mma/run.py`: CuTe's own host code builds the tensor maps
and launch parameters, and the results are the same.

## Triton

`warplens.triton_driver.install("B200")` makes Triton compile for `sm_100a`
and launch into the simulator. Triton's bundled toolchain does the compiling;
no GPU or CUDA driver is involved. `kernel[grid](...)` then works as usual,
with tensors created by `gpu.tensor(numpy_array)` and `gpu.empty(shape,
dtype)`. `warplens run script.py` installs the driver and runs the script.

`uninstall()` restores the driver state preceding `install()` without probing
for a physical GPU; installs may be nested. `active_driver()` returns the active
warplens driver, or `None`, without initializing Triton's hardware backend.
Tensors belong to the driver that allocated them and cannot be passed to a
different simulated device. Kernel caches are separate from real CUDA devices.

Tuple arguments (including nested constexprs), launch hooks, empty grids and
`tl.device_print` are supported. With `num_ctas > 1`, grid dimensions count
Triton programs: each program launches a cluster of `num_ctas` physical CTAs.

Triton's matmul compiles to a `tcgen05.mma` on this target, so it exercises the
same tensor core as the CUTLASS examples by a different code generator. It
needed: MN-major MMA operands, `ldmatrix`, `bfe`, `prmt`, and the older
per-thread `cp.async` with commit and wait groups. Each of the last four was
checked against the RTX 3080 Ti.

Running the matmul under the timing model exposed a real bug:
`cp.async.wait_group N` counted pending groups instead of waiting for all but
the N most recently committed ones. The two agree when copies finish in the
order they were issued, which untimed runs guarantee and timed runs do not.

Copy groups and waits are tracked per thread, including empty commits.
The hazard checker's acquired knowledge is still stored per warp, so it can
miss cross-lane misuse after only some lanes wait. The timing model charges
`cp.async` against the TMA resource's rates and startup latency, and its source
lines to L2 or HBM by the same record as a TMA load's; this is an
approximation, not a model of the separate hardware copy path or its caches.
Zero-filled bytes count toward the shared-memory transfer, but not HBM traffic.

## Runtimes that launch for themselves: TIRx and the CuTe DSL

Step A3 of the plan asked which driver calls these two make and what they hand
the driver. Both were traced on an RTX 3080 Ti with a debugger breaking on
every export of `libcuda`.

| | TIRx (`apache-tvm-tirx` 0.1.0) | CuTe DSL (`nvidia-cutlass-dsl` 4.8.1) |
| --- | --- | --- |
| Who launches | TVM's runtime library, linked against `libcudart` and `libcuda` | host code the DSL compiles, calling wrappers in `libcute_dsl_runtime.so` |
| CUDA runtime | the shared `libcudart.so.13` | NVIDIA's, linked into `libcute_dsl_runtime.so`; cuda-python has another copy |
| Calls for a launch | `cuModuleLoadData`, `cuModuleGetFunction`, `cuFuncGetAttribute`, `cuDeviceGetAttribute`, `cuLaunchKernelEx`; memory through `cudaMalloc` and `cudaMemcpyAsync` | `cudaLibraryLoadData`, `cudaLibraryGetKernel`, `cuKernelGetAttribute`, `cudaKernelSetAttributeForDevice`, `cudaLaunchKernelExC` |
| What the driver is handed | machine code by default; PTX text if the script asks (`target_format`) | a fat binary with one entry of machine code, never PTX |

A copy of the CUDA runtime that is linked into a library cannot be replaced by
preloading, and it will not start on the `libcuda` shim: it asks the driver for
private tables (`cuGetExportTable`) and gives up without them. An experiment
that refused them got past the first table and failed at the second. Faking
those tables was not pursued. The two runtimes are reached differently instead.

### TIRx

```bash
warplens run python examples/07_tirx/run.py
```

TVM's runtime uses the shared libraries, so the two shims serve it once they
have the calls in the table. It asks the device for its compute capability,
gets 10.0 (10.3 for `--model B300`) and compiles for `sm_100a` (`sm_103a`)
with NVRTC, in process. The script has to ask for PTX,

```python
with T.device_entry(launch=..., backend_config={"cuda": {"target_format": "ptx"}}):
```

because the default is machine code. A module of machine code is refused with
that advice. The same script runs on a GPU, whose driver takes PTX too, provided
the driver is at least as new as the NVRTC that wrote the PTX. Arrays are TVM's
own (`tvm_tirx.runtime.tensor`), which use `cudaMalloc`.

- NVRTC must know `sm_100a`: the env now includes `cuda-nvrtc` 13.5. With an
  older one first on the path, compilation fails on the architecture name.
- TIRx compiles with fast-math, which is why `.ftz` arithmetic is now
  implemented (`coverage.md`; checked on the GPU, `validation/README.md`).
- `T.cuda.printf` becomes a device function that is called, not inlined.
  Such calls are supported (`coverage.md`).
- The book's scripts create their arrays with PyTorch on the GPU. PyTorch does
  not run on the shims, so those scripts need TVM arrays in their place.

All nine GEMM kernels of the book run this way and match NumPy:

```bash
git clone https://github.com/mlc-ai/modern-gpu-programming-for-mlsys book
warplens run python examples/08_book/run.py book
```

The runner executes the `hgemm_v1` to `hgemm_v9` definitions from the chapters
of the clone (the book has no license, so they are not copied here), with TVM
arrays and a target that asks for PTX. Each kernel gets the smallest problem it
does any work on, up to 512 x 256 x 256 for the two-CTA `v9`. Getting there
needed three things in the simulator: calls to device functions, `mapa.u64`
on generic addresses, and a decision about `v7` to `v9` releasing their tensor
memory once per warpgroup. The repeats are ignored and reported as
`tmem-dealloc-repeated`; what hardware does with them is not known.
`WARPLENS_DUMP_PTX=<directory>` keeps the PTX a program hands over.

### CuTe DSL

```bash
warplens run python examples/06_cute_dsl/run.py
```

`warplens run` arranges three things, all through the DSL's own settings, and
the script is not involved:

1. **The runtime library.** The DSL also ships its wrappers as a static
   archive that leaves the CUDA runtime to the linker.
   `warplens/shim/build_cute_dsl.sh` links that archive against the `libcudart`
   shim, and `CUTE_DSL_LIBS` makes the DSL launch through the result. It is
   built on first use from the installed package; nothing is copied. Runtime
   functions the archive names and the shim lacks (30 of them: graphs,
   managed and asynchronous memory, and others) fail when called.
2. **The PTX.** `CUTE_DSL_KEEP=ptx` and `CUTE_DSL_DUMP_DIR` make the DSL write
   the PTX of every kernel it compiles. The module the host code loads is
   machine code; the server accepts it and finds each kernel by name in the
   newest kept file that defines it at module-load time. Sources are frozen then,
   so a later compilation with the same kernel name cannot change an already
   loaded module. `CUTE_DSL_ARCH` is set to `sm_100a` or
   `sm_103a`. Keeping artifacts turns off the DSL's compile cache.
3. **The device count.** Before a launch the DSL's Python asks cuda-python's
   runtime module how many devices there are. That module is the second
   built-in runtime. A `sitecustomize.py` put first on `PYTHONPATH` answers
   that one call; it runs any `sitecustomize` it hides.

Settings the user has already made are left alone, except that `ptx` is added
to `CUTE_DSL_KEEP`.

**Arrays.** DSL examples hold their arrays in PyTorch tensors on the GPU, and
PyTorch does not run on the shims. `examples/06_cute_dsl/saxpy.py` holds them
the way the DSL does underneath: device memory from the driver, through the
DSL's own helpers (`cutlass.base_dsl.runtime.cuda`), passed as pointers
(`make_ptr`). Those helpers use cuda-python's driver module, which finds every
driver function by name (`cuGetProcAddress`); the `libcuda` shim has the
context, memory and stream calls it then makes. The script runs unchanged on a
GPU. An array from any library that allocates through the shared CUDA runtime
and speaks DLPack also works with `from_dlpack`; TVM's tensors do.

**Not working: kernels that use TMA.** CUTLASS's Blackwell tutorial
`fp16_gemm_0.py` compiles, its host function runs and the kernel is launched
in the simulator, with TVM arrays in place of the tutorial's PyTorch ones. The
launch stops at the first `cp.async.bulk.tensor`. The DSL does not ask the
driver for its tensor maps (`cuTensorMapEncodeTiled` is never called); its
compiled host code writes the 128-byte descriptor itself, in the driver's own
undocumented layout, and the simulator only reads descriptors it made. The
first 64 bytes are plainly the address, the stride, the dimensions and the box
in some packing, but a decoder written from a handful of samples could not be
checked: the driver on this machine refuses to encode a tensor map for an
Ampere GPU (`CUDA_ERROR_NOT_SUPPORTED`). On a B200 the driver's encoder can be
swept over its parameters and the bytes saved; a decoder can then be written
and tested against them with no GPU. That sweep belongs in the probe suite.
The DSL's experimental `create_tensor_map_tiled` API appears to go through the
driver instead and might work already; it was not tried.

## Limits

- **Build flags are required** for compiled programs. A binary with only
  machine code is reported with the flags to use; it cannot be simulated.
- **The shim covers what the four tutorials, TVM's runtime and the CuTe DSL
  call**, about sixty functions. A program that calls anything else fails to
  start with an unresolved symbol, or silently reaches the real runtime if that
  is installed: only the listed functions are replaced. Multiple devices,
  unified memory, textures and `cudaMemcpy2D` are not there. Streams and events
  are tokens.
- **A CUDA runtime linked into the program or into a library it loads** cannot
  be replaced. That rules out PyTorch and cuda-python's runtime module.
- Everything is synchronous and single-device. Context handles name one simulated
  context; nested pushes and pops preserve the per-thread current-context stack.
  The driver exposes compatible entry points for each supported context API
  signature requested through `cuGetProcAddress`. `cudaFree` releases its allocation.
- The shim libraries are Linux-only and are compiled on first use; that needs
  a C compiler and the CUDA headers. The runtime `cudaLibrary*` API used by the
  CuTe DSL needs CUDA 12.8 or newer headers; the driver shim also builds with 12.4.
- Triton: no torch tensors, no benchmarking interface, no kernels that need a
  global or profile scratch buffer, and no host tensor descriptor arguments.
  The compiler target is `sm_100a` for both models; selecting B300 changes the
  simulator's timing configuration, not Triton's compiler target. The driver
  adapter is tested against Triton 3.9, including runs with GPU discovery denied.
  Multi-CTA launch grids are supported, but some Triton multi-CTA matmuls emit
  unsupported TMEM transfer shapes such as `tcgen05.st.16x32bx2` and fail explicitly.
- CuTe DSL: see above.
