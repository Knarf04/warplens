# M3: tcgen05 and tensor memory

M3 adds the Blackwell tensor core (`tcgen05.mma`), tensor memory (TMEM), and
the general PTX that real CUTLASS kernels need around them. The first two
CUTLASS Blackwell tutorials run unmodified and are correct, and every
acceptance item that does not need clusters is met.

```
$ conda run -n warplens examples/03_cutlass_mma/build.sh
$ python examples/03_cutlass_mma/run.py
tutorial 1, GEMM 256 x 512 x 128: max abs error vs NumPy 6.68e-06 (relative 3.92e-07)
  4 CTA(s), 75294 warp-instructions, 0 finding(s), 17 line(s) printed by the kernel
tutorial 2, GEMM 256 x 512 x 128: max abs error vs NumPy 6.68e-06 (relative 3.92e-07)
  4 CTA(s), 21061 warp-instructions, 0 finding(s), 22 line(s) printed by the kernel
```

## How much to trust it

Nothing here has run on Blackwell hardware. Two things stand in for that:

- **CUTLASS agrees.** The tutorial builds its shared-memory layouts, its
  descriptors and its TMEM addressing with CuTe's layout algebra, which is
  written against the real hardware. warplens decodes those descriptors and
  addresses independently, and the GEMM comes out right. A wrong swizzle,
  descriptor field, row-to-lane mapping or `tcgen05.ld` lane assignment would
  have scrambled the result.
- **The general PTX was checked on an RTX 3080 Ti**: `printf`, by-value struct
  parameters, local arrays and vector stores print exactly what the GPU prints,
  and vector `mov` packs its first element into the low half as on the GPU.

What this does not cover: timing, the order of additions inside one MMA, and
anything the tutorials do not exercise. M = 64, unswizzled and 32B/64B
operands, and tf32 are tested only against warplens's own reading of the layout
comments in `cute/arch/mma_sm100_desc.hpp`. The 16-lane load/store shapes are
tested against CuTe's layout definitions but no CUTLASS kernel using them has
been run.

## Known ordering limitation

Generic-to-async proxy ordering for MMA shared-memory operands is not diagnosed.
The [PTX shared-memory access rule](https://docs.nvidia.com/cuda/parallel-thread-execution/#tcgen05-memory-consistency-model-shared-memory-accesses)
requires a proxy fence, while the pinned CUTLASS tutorial 01 (`f8acf1aa`) uses
ordinary shared stores followed by `bar.sync` and MMA, with no `fence.proxy.async`
in its generated PTX. This specification/example discrepancy remains unresolved;
warplens makes no hardware-correctness claim about that sequence. Uninitialized
operands and missing synchronization with TMA producers are checked separately.

TMEM loads and stores currently complete synchronously, so `tcgen05.wait::ld/st`
validate warp participation but do not model a separate completion delay.
`fence::after_thread_sync` acquires MMA completion observed by a successful
relaxed mbarrier wait. General before/after-fence ordering across other
inter-thread synchronization patterns is not yet diagnosed.

## Design

**TMEM** (`units/tcgen05.py`) is 128 lanes x 512 columns of 32 bits per CTA; an
address is `(lane << 16) | column`. `tcgen05.alloc` reserves a power-of-two
number of columns (at least 32) and writes the address to shared memory.
Both explicit shared and generic shared destinations are supported. An
allocation waits if TMEM is full; another warp's deallocation can release it.
Later allocations cannot increase the requested size or follow
`tcgen05.relinquish_alloc_permit`. Deallocation must name the returned base
address and the original size. These rules follow the
[PTX allocation contract](https://docs.nvidia.com/cuda/parallel-thread-execution/#tcgen05-instructions-tcgen05-alloc).

**`tcgen05.mma`** decodes the instruction descriptor (M, N, formats, negation)
and the two shared-memory descriptors (start, leading and stride byte offsets,
swizzle), reads A (M x K) and B (N x K) from shared memory in K-major layout,
and writes or accumulates `A * B^T` as float32. With `enable-input-d`, the
optional `scale-input-d` scales the previous accumulator by `2^-scale` (0–15).
K is 32 bytes of elements: 16
for half precision, 8 for tf32. Row m of the result is lane m for M = 128, and
lane `32 * (m // 16) + m % 16` for M = 64. The docstring of `units/tcgen05.py`
states each rule and the CuTe header it comes from.

**MMA is asynchronous**, like TMA. It completes `async_delay` rounds after it
is issued. Each `tcgen05.commit` tracks all prior MMAs from its issuing thread;
another lane's commit cannot cover them. Multiple commits can track the same
earlier operations on different barriers. A successful acquire wait, or a
successful relaxed wait followed by `tcgen05.fence::after_thread_sync`, makes
those MMA results visible to the waiting warp. Generic shared-memory barrier
addresses are supported. Read-only/partial MMA commits are rejected.

**`tcgen05.ld.32x32b.xN [addr]`** gives the thread on lane l the columns
starting at `column(addr)` of TMEM lane `lane(addr) + l`. The `16x64b`,
`16x128b` and `16x256b` shapes cover 16 lanes and give each thread 1, 2 or 4
registers per unit, spread over lanes and columns; `transfer_cells` in
`units/tcgen05.py` has the mapping, and
`python -m warplens.viz.tmem --transfer 16x128b 1` prints it.
Loads and stores require all 32 lanes of the warp and a uniform TMEM base
address. Allocation, deallocation, waits and permit relinquishment also
require the full warp; allocation and deallocation require uniform column
counts. Unsupported transfer modifiers and repetition counts are rejected.

**Tensor maps by value.** CUTLASS keeps each tensor map inside a copy atom
that is a kernel argument, and takes its address with `mov` and `cvta.param`.
Parameters therefore have an address space of their own, and TMA reads the
tensor map from wherever the pointer leads. The host passes
`TensorMap.tobytes()` inside the struct; it is warplens's encoding, not the
driver's.

**General PTX added for CUTLASS:** `.global`/`.const` data, per-thread `.local`
memory, structs passed by value, `.v2`/`.v4` loads and stores, vector `mov`,
`elect.sync`, and `call` to `vprintf`. Text printed by the kernel is returned
in `stats.output`.
CUDA `printf` returns the number of parsed arguments, including zero for a
literal-only format. Parameter blobs are cached per launch without relying
on recyclable object IDs. Parameter-pointer loads and constant loads are
supported, local variables obey lexical scope, and vector shared-memory
accesses count as one full-width instruction in the bank report.

## Findings added

| Finding | Meaning |
| --- | --- |
| `tmem-read-before-commit` | accumulators read while their MMA is in flight, or without waiting on the commit's mbarrier |
| `tmem-write-before-commit` | a TMEM store overwrites an MMA destination without synchronizing with its producer |
| `tmem-dealloc-before-commit` | an allocation is released before its MMA producers have been synchronized with |
| `tmem-lane-rule` | a warp touched TMEM lanes outside `32 * (warpid % 4) .. + 31` |
| `tmem-uninitialized-read` | load or MMA accumulation reads TMEM cells never written |
| `tmem-unallocated` | MMA, load or store on columns that are not allocated |
| `tmem-leak` | columns still allocated when the kernel returned |
| `mma-operand-overwritten` | shared memory written while an MMA was reading it |
| `smem-uninitialized-read` | MMA reads shared operands that were never initialized |
| `tma-load-unsynchronized` | MMA consumes a TMA-loaded operand without acquiring its completion |
| `mma-swizzle-mismatch` | an operand's descriptor names a different swizzle than the TMA load that wrote the buffer |
| `tcgen05-not-waited` | the kernel returned with an MMA or commit in flight |

## Not implemented

- `cta_group::2`, `tcgen05.commit` with multicast (M5).
- Operand A from TMEM (`_TS` forms), MN-major operands, bf16, integer and
  f8f6f4 kinds, block scaling, sparsity, float16 accumulators.
- `tcgen05.ld`/`st` with `.pack::16b` / `.unpack::16b`, the `16x32bx2` shape,
  `tcgen05.cp`, `tcgen05.shift`.
- Exclusive TMEM allocation and deallocation (`.exclusive`).
- A libcuda shim. To run a CUTLASS kernel today, the caller builds its by-value
  arguments by hand, as `examples/03_cutlass_mma/run.py` does, including the
  box and swizzle of each tensor map, which CuTe would otherwise derive.
