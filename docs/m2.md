# M2: TMA and mbarrier

M2 adds asynchronous bulk copies between global and shared memory (TMA), the
tensor maps that describe them, mbarriers, proxy fences, and checkers for the
ways this protocol is usually broken.

```
$ python examples/02_tma_copy/run.py
Round trip GMEM -> SMEM -> GMEM for each swizzle mode:
  swizzle  None, box (16, 32): correct, 0 finding(s)
  swizzle   32B, box (16, 8): correct, 0 finding(s)
  swizzle   64B, box (16, 16): correct, 0 finding(s)
  swizzle  128B, box (16, 32): correct, 0 finding(s)

== bug 1: expect_tx too small
output correct
[mbarrier-tx-mismatch] 2048 byte(s) delivered to an mbarrier phase that expected only 1024 more. ...
  line 73: cp.async.bulk.tensor.2d.shared::cluster.global.mbarrier::complete_tx::bytes [%r12], ...
```

## Acceptance

| Criterion | Result |
| --- | --- |
| A TMA copy kernel round-trips GMEM -> SMEM -> GMEM for every swizzle mode | met: `tests/test_tma.py::test_round_trip_for_every_swizzle_mode` |
| Wrong `expect_tx` is caught | met, both ways: too small is a `mbarrier-tx-mismatch` finding, too large is a `DeadlockError` that names the mbarrier and the bytes it still expects |
| Missing fence is caught | met: `tma-store-missing-fence` |
| Early reuse is caught | met: `tma-store-source-overwritten`; a skipped mbarrier wait gives `tma-load-unsynchronized` |

The example kernel is CUDA C++ with the same inline PTX that CUTLASS uses for
these operations, compiled by nvcc for `sm_100a`; `ptxas` accepts it.

**Nothing in M2 has been compared with hardware.** The development GPU is
Ampere, which has no TMA. The semantics here come from the CUDA 13.5 headers,
the CUTLASS sources and the plan's design notes. The points most worth
confirming on a real Hopper or Blackwell GPU are listed under *Assumptions*.

## Design decisions

**Tensor maps are warplens's own encoding.** A real `CUtensorMap` is 128
opaque bytes written by the driver. `Device.tensor_map_tiled` plays the role
of `cuTensorMapEncodeTiled`, applies the same documented argument checks, and
writes a 128-byte record that the TMA unit decodes (`host/tensor_map.py`). The
kernel receives a pointer to it in global memory. `box` is given in the
array's NumPy axis order; TMA coordinates inside the kernel are innermost
first.

**A TMA instruction issues a copy; the copy completes later.** Completion is an
event `async_delay` scheduling rounds after issue (default 4), or immediately
if no warp can run. A load reads global memory when issued and writes shared
memory when it completes, then performs `complete_tx` on its mbarrier. A store
reads shared memory when it completes.

**mbarrier.** Each mbarrier tracks pending arrivals and expected bytes for its
current phase; the phase completes when both are zero. Every lane that executes
an `arrive` arrives. `try_wait` blocks the warp until the phase completes
instead of returning false, so a wait that can never succeed becomes a
deadlock report. `test_wait` never blocks.

**Checks do not depend on timing.** Shared memory records, per byte, the TMA
load that last targeted it and the TMA store that last read it. Each warp keeps
the set of copies it has synchronized with: by a successful mbarrier wait, by
`wait_group`, or by meeting another warp at a barrier or mbarrier that already
had. Touching bytes of a copy outside that set is reported, even when the data
happened to arrive in time. The tests run the broken kernels with delays of 0,
4 and 1000 rounds and get the finding each time.

**Fences.** An ordinary store marks its bytes as not yet visible to TMA.
`fence.proxy.async` clears the mark for the warp's own writes and for writes
that a completed barrier already ordered before it. A TMA store of marked bytes
is reported. Other fences are accepted and have no effect.

**Inline assembly.** nvcc passes `asm` blocks through, including `{ ... }`
blocks with their own `.reg` declarations and labels (the mbarrier wait loop).
The parser gives each block a scope; names declared in it are stored as
`name@scope`.

## Findings added

| Finding | Meaning |
| --- | --- |
| `mbarrier-tx-mismatch` | TMA delivered more bytes than the phase expected: `expect_tx` is missing, too small, or late |
| `mbarrier-over-arrival` | more arrivals than the phase needed |
| `mbarrier-init-race` | an mbarrier used by another warp with no barrier since its `init` |
| `tma-load-unsynchronized` | ordinary read or write (or TMA store) of bytes a TMA load writes, without having waited on its mbarrier |
| `tma-store-missing-fence` | TMA store of bytes written by ordinary stores with no `fence.proxy.async` |
| `tma-store-source-overwritten` | write to bytes a TMA store reads, before waiting for it |
| `tma-store-not-waited`, `tma-load-not-waited` | the kernel returned with the copy still in flight |
| `tma-swizzle-misaligned` | a swizzled buffer not aligned to the swizzle period |

Use of an mbarrier before `mbarrier.init`, a TMA instruction whose rank differs
from its tensor map's, and a pointer that is not a tensor map are errors.

## Assumptions to confirm on hardware

- **Swizzle is a function of the shared-memory address**, not of the offset
  into the buffer: CuTe's `Swizzle<B,4,3>` with B = 1, 2, 3 for 32B, 64B, 128B,
  applied to the address. The two views agree when the buffer is aligned to the
  swizzle period (256, 512, 1024 bytes), which is why misalignment is reported.
- **`complete_tx` counts the whole box**, including out-of-bounds elements that
  were filled rather than read.
- **The NaN used for out-of-bounds fill** is NumPy's default quiet NaN; the
  hardware constant is not documented.
- **Fence scope**: that a fence after a barrier covers other warps' earlier
  writes.

## Not implemented

- `.multicast::cluster` and cluster-wide shared memory (M5), im2col mode,
  interleaved layouts, `cp.reduce.async.bulk`, `tensormap.replace`.
- `mbarrier.arrive_drop`, `.noComplete`, `mbarrier.pending_count`.
- Tensor maps passed by value in the kernel's parameters, as CUTLASS does;
  that needs array parameters and comes with M3.
- The ABA check from the plan (waiting on a parity two phases behind).
- The L2 promotion and cache-hint settings are accepted and ignored.
