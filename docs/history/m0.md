# M0: skeleton

> **A development record, not the manual.** This is the write-up of milestone M0 (the executor): its
> acceptance results, the decisions made, and what was known when it was last edited. It is no
> longer updated. What it says about hardware may predate the B200 run of 2026-11-25, and what
> it lists as not implemented may exist since. Current: the [user guide](../guide.md) (section 2
> for what has been checked against a GPU, section 8 for limits) and
> [architecture.md](../architecture.md#2-the-warp-executor), which carries this design forward.

M0 runs kernels that nvcc compiled for `sm_100a` on the CPU and checks them
against NumPy. It covers the PTX parser, the SIMT warp executor, global
memory and the Python launch API. Nothing Blackwell-specific exists yet.

```python
import numpy as np, warplens

sim = warplens.Device("B200")
A, B = sim.from_numpy(a), sim.from_numpy(b)
C = sim.empty(n, "f32")
sim.launch("examples/00_vecadd/vecadd.ptx", "vecadd", grid=4, block=256, args=[A, B, C, n])
assert np.array_equal(C.numpy(), a + b)
```

| `classify` | if/else with stores on both sides, inside a loop with `break` | `test_classify_nested_branches_with_early_exit` |

The `.ptx` files are checked in next to their `.cu` sources, so tests and CI
need no CUDA install. Regenerate them with
`conda run -n warplens examples/build_ptx.sh`.

## Design decisions

**Registers hold raw bits.** nvcc declares most registers as `.b32` / `.b64`
and lets each instruction choose the interpretation (`add.f32 %r8, %r6, %r7`
on `.b32` registers). A register is therefore 32 unsigned integers of its
width, and `Warp.read(operand, type)` reinterprets them per instruction.

**A warp executes one instruction on 32 lanes at once** as NumPy arrays, and
writes results only to lanes in the active mask. Lanes past the end of a
partial warp are never active.

**Divergence uses a reconvergence stack** (`core/simt_stack.py`). When lanes
disagree at a branch, the warp splits into one stack entry per side, and the
sides rejoin at the branch's immediate post-dominator (`frontend/cfg.py`).
The stack also performs a rendezvous at named CTA barriers and `tcgen05` `.sync.aligned`
instructions: pending paths run until every non-exited lane reaches the same
instruction. This is necessary when the static postdominator lies beyond the
actual join, including joins inside cycles. The early grouping policy below
does not imply a hardware guarantee for unsynchronized communication. Rendezvous at
different instruction addresses or across divergent recursive activations is
explicitly unsupported.

Four other cases needed care:

- *Loops.* A loop branch reconverges at the loop exit on every iteration. If
  the top entry already rejoins there, it is replaced rather than nested, so
  stack depth does not grow with the trip count.
- *Early `ret`.* Returning lanes are removed from every stack entry, so they
  cannot be revived when an outer region reconverges.
- *Infinite loops.* Blocks that cannot reach the exit get a virtual edge to
  it, so a branch into such a loop reconverges nowhere.
- *Lanes that meet before the post-dominator.* In
  `if (a) {...; goto join;} if (b) return; join: ...` the first branch's
  post-dominator is the return, yet every lane that stays passes `join`. The
  recorded Ampere programs run them as one group from `join` on
  (`validation/ampere/reconvergence_golden.py`). To reproduce this scheduling
  choice, among the stack entries that rejoin at the same pc, an entry that
  can still reach the pc of the top one (and cannot be reached from it) runs
  first, and entries at the same pc are merged (`core/warp.py`, `_regroup`).
  Entries on a common cycle keep their order.

**The engine steps warps round-robin, one instruction each.** Running each
warp to completion would be simpler and faster now, but M2 needs warps to
interleave with the TMA engine and with each other. Other orders can be
chosen since: [scheduling.md](../scheduling.md).

**Global memory faults on stray accesses.** Allocations are separated by
unmapped gaps. An out-of-bounds load or store raises `MemoryFault` with the
PTX line, CTA, warp, lane and thread.

**Device arrays belong to their allocating device.** Launch arguments from
another `Device` are rejected before execution, even when their numeric
addresses match a local allocation.

**Fused multiply-add rounds once.** `fma` and floating-point `mad` combine
integer significands exactly before rounding to the destination format.
This portable path also handles cancellation, subnormals and signed zero;
it trades some throughput for correct rounding without extra dependencies.

**Unsupported PTX is a hard error.** Unknown opcodes are rejected when the
kernel is launched, before anything runs. Unknown modifiers are rejected when
the instruction executes. See `coverage.md`.

## Known limits

- CTAs run one after another, so races between CTAs on global memory are not
  explored.
- Blocking waits arrived in M1; see `m1.md`.
- Misaligned loads and stores are allowed.
- Speed: about 70k warp-instructions per second on a laptop (vecadd on 262k
  elements takes 2.6 s). Fine for tile-sized problems; revisit before M3.
