# M3: tcgen05 and tensor memory

M3 adds the Blackwell tensor core (`tcgen05.mma`), tensor memory (TMEM), and
the general PTX that real CUTLASS kernels need around them. **M3 is partly
done**: the first CUTLASS Blackwell tutorial runs unmodified and is correct;
the second one, and the TMEM layout view, are still open.

```
$ conda run -n warplens examples/03_cutlass_mma/build.sh
$ python examples/03_cutlass_mma/run.py
GEMM 256 x 512 x 128: max abs error vs NumPy 6.68e-06 (relative 3.92e-07)
4 CTA(s), 75294 warp-instructions, 0 finding(s), 17 line(s) printed by the kernel
```

## How much to trust it

Nothing here has run on Blackwell hardware. Two things stand in for that:

- **CUTLASS agrees.** The tutorial builds its shared-memory layouts, its
  descriptors and its TMEM addressing with CuTe's layout algebra, which is
  written against the real hardware. warplens decodes those descriptors and
  addresses independently, and the GEMM comes out right. A wrong swizzle,
  descriptor field, row-to-lane mapping or `tcgen05.ld` lane assignment would
  have scrambled the result.
- **The general PTX was checked on an RTX 3080 Ti**: `printf`, by-value struct
  parameters, local arrays and vector stores print exactly what the GPU prints,
  and vector `mov` packs its first element into the low half as on the GPU.

What this does not cover: timing, the order of additions inside one MMA, and
anything the tutorial does not exercise (M = 64, unswizzled and 32B/64B
operands, tf32 are tested only against warplens's own reading of the layout
comments in `cute/arch/mma_sm100_desc.hpp`).

## Design

**TMEM** (`units/tcgen05.py`) is 128 lanes x 512 columns of 32 bits per CTA; an
address is `(lane << 16) | column`. `tcgen05.alloc` reserves a power-of-two
number of columns (at least 32) and writes the address to shared memory.

**`tcgen05.mma`** decodes the instruction descriptor (M, N, formats, negation)
and the two shared-memory descriptors (start, leading and stride byte offsets,
swizzle), reads A (M x K) and B (N x K) from shared memory in K-major layout,
and writes or accumulates `A * B^T` as float32. K is 32 bytes of elements: 16
for half precision, 8 for tf32. Row m of the result is lane m for M = 128, and
lane `32 * (m // 16) + m % 16` for M = 64. The docstring of `units/tcgen05.py`
states each rule and the CuTe header it comes from.

**MMA is asynchronous**, like TMA. It completes `async_delay` rounds after it
is issued. `tcgen05.commit` arrives on an mbarrier once the MMAs issued before
it are done, and a warp that waits on that mbarrier has synchronized with them.

**`tcgen05.ld.32x32b.xN [addr]`** gives the thread on lane l the columns
starting at `column(addr)` of TMEM lane `lane(addr) + l`.

**General PTX added for CUTLASS:** `.global`/`.const` data, per-thread `.local`
memory, structs passed by value, `.v2`/`.v4` loads and stores, vector `mov`,
`elect.sync`, and `call` to `vprintf`. Text printed by the kernel is returned
in `stats.output`.

## Findings added

| Finding | Meaning |
| --- | --- |
| `tmem-read-before-commit` | accumulators read while their MMA is in flight, or without waiting on the commit's mbarrier |
| `tmem-lane-rule` | a warp touched TMEM lanes outside `32 * (warpid % 4) .. + 31` |
| `tmem-uninitialized-read` | read of TMEM cells never written |
| `tmem-unallocated` | MMA, load or store on columns that are not allocated |
| `tmem-leak` | columns still allocated when the kernel returned |
| `mma-operand-overwritten` | shared memory written while an MMA was reading it |
| `tcgen05-not-waited` | the kernel returned with an MMA or commit in flight |

## Not implemented

- `cta_group::2`, `tcgen05.commit` with multicast (M5).
- Operand A from TMEM (`_TS` forms), MN-major operands, bf16, integer and
  f8f6f4 kinds, block scaling, sparsity, float16 accumulators.
- `tcgen05.ld`/`st` shapes other than 32x32b, `.pack::16b`, `tcgen05.cp`,
  `tcgen05.shift`.
- A libcuda shim. To run a CUTLASS kernel today, the caller builds its by-value
  arguments by hand, as `examples/03_cutlass_mma/run.py` does.
