# M5: clusters

M5 adds cluster launches: CTAs that run together, reach each other's shared
memory and mbarriers, receive each other's TMA loads, and share one MMA
between two of them.

```
$ conda run -n warplens examples/03_cutlass_mma/build.sh
$ python examples/03_cutlass_mma/run.py 3
tutorial 3, GEMM 512 x 1024 x 128: max abs error vs NumPy 8.58e-06 (relative 4.64e-07)
  16 CTA(s), 76006 warp-instructions, 0 finding(s), 25 line(s) printed by the kernel
$ python -m warplens.viz.tmem 128 16 --pair

  even   0-63       rows 0-63, columns 0-7 in TMEM columns 0-7
  even   64-127     rows 0-63, columns 8-15 in TMEM columns 0-7
  ...
```

**Nothing here has run on Blackwell hardware.** As in M3, the evidence is that
CUTLASS's own kernels come out right: byte counts on the mbarriers balance
exactly and the GEMM matches NumPy only if multicast targets, the leader/peer
accounting and the two-CTA result placement are all as modeled.

## Design

**A launch is made of clusters.** `sim.launch(..., cluster=(4, 4, 1))` groups
the grid's CTAs; without it each CTA is a cluster of one. The engine schedules
a whole cluster, so warps of different CTAs interleave. A CTA's rank in its
cluster is `x + nx * (y + ny * z)`. The special registers `%cluster_ctarank`,
`%cluster_nctarank`, `%cluster_ctaid`, `%cluster_nctaid`, `%clusterid`,
`%nclusterid` and `%is_explicit_cluster` are provided. Clusters hold at most
16 CTAs, the width of a multicast mask.

**Cluster barrier.** `barrier.cluster.arrive` registers the warp and snapshots
the synchronization knowledge it releases (unless `.relaxed` is specified);
`barrier.cluster.wait` blocks until every running warp of the cluster has
arrived. A duplicate arrival before the current phase completes is an error.
An aligned barrier reached by only part of a warp produces a finding;
divergent non-aligned cluster rendezvous is not modeled and is rejected.

**TMA multicast.** A load with `.multicast::cluster` and a 16-bit mask writes
the same box at the same shared-memory offset in every CTA whose rank is in
the mask, and performs `complete_tx` on each one's mbarrier at the given
offset. With `.cta_group::2` the barrier pointer can select either member of
the receiving pair. Multicast completions use that pointer's CTA-rank parity
to choose the corresponding member of every receiving pair.

**Commit multicast.** `tcgen05.commit ... .multicast::cluster` arrives on the
mbarrier at that offset in every CTA of the mask.

**Two-CTA MMA** (`cta_group::2`). Issued by one thread from either CTA of a pair. Each
CTA holds half of A's rows and half of B's rows in its own shared memory at the
same descriptor addresses, and receives its half of the result in its own
tensor memory:

- M = 256: 128 rows on 128 lanes per CTA, N columns.
- M = 128 (PTX's Layout B): 64 rows per CTA. They fill half the lanes, so the
  columns are folded: columns below N/2 on lanes 0-63, the rest on lanes
  64-127, in N/2 TMEM columns.

`tcgen05.alloc`, `dealloc` and `relinquish_alloc_permit` with `cta_group::2`
act on the issuing CTA's own tensor memory; both CTAs of a pair run them and
get the same columns.

**Distributed shared memory.** `mapa.shared::cluster` turns a shared address
into the cluster-wide address of the same location in another CTA.
`ld`/`st.shared::cluster` and `mbarrier.arrive.shared::cluster` accept such
addresses. Other mbarrier operations on a remote mbarrier are errors.

**Synchronization knowledge** (which TMA copies and MMAs a warp may rely on)
crosses CTAs: operation ids are unique within a cluster, and the cluster
barrier and remote or multicast arrivals carry knowledge as local ones do.

## Limits

- CLC is not implemented.
- The encoding of cluster-wide addresses is warplens's own.
  Shared symbols and `mapa` pointers carry absolute CTA rank bits above the
  byte offset. Bit 24 selects the peer within a pair so CUTLASS's
  `Sm100MmaPeerBitMask` address arithmetic works; the remaining encoding is
  simulator-defined.
- In a timed run a multicast load is charged to each receiving SM as if it
  were its own copy, and a two-CTA MMA is charged to the issuing SM only.
- Shared-memory race checks do not span CTAs: a remote store is recorded, but
  races between CTAs are not reported, and remote accesses are left out of the
  bank-conflict report.
- CTAs of different clusters never run concurrently.
  CTAs within a cluster share pending L2-fill times; a fetch cannot become an
  L2 hit in a peer before it completes. Prior clusters' fetched lines start warm.
  Outstanding async operations are diagnosed at each CTA's exit, even while
  its peers continue running.
- `cta_group::2` with FP16/TF32 operands and either issuing CTA has regression
  coverage for M = 128/256. Layout A/B views reject nonzero lane offsets.
  Layouts for `.ws` MMAs and structured sparsity do not exist.
- As for tutorials 1 and 2, the caller builds the kernel's arguments by hand,
  including each tensor map's box: with multicast a CTA loads only part of a
  tile (a quarter of A's rows here), which CuTe would otherwise derive.
