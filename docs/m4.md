# M4: timing and reports

M4 adds an approximate timing model, GPU configs in which every number has a
source, a Perfetto trace, a utilization summary with a bottleneck verdict, an
HTML timing report, and the `warplens report` command, which puts every static
view of a run on one page.

**The timings are illustrations, not predictions.** The model is uncalibrated,
the microarchitecture is not public, and several parameters are assumptions:
the core clock, the TMA engine's latency and throughput, the L2 rate, and the
costs of shared-memory, TMEM and global accesses. The config files mark each
one. What the model is good for is showing *why* a kernel is limited by what it
is limited by under stated parameters.

```
$ python examples/04_pipelined_gemm/run.py out/

       4      14,617         891   HBM             14%   99%     9%
```

## Acceptance

| Criterion | Result |
| --- | --- |
| A warp-specialized pipelined GEMM shows the expected trend over 1/2/4 stages (latency, then TMA/HBM, then Tensor Core) | **met in part, and the plan's expectation needs correcting.** `examples/04_pipelined_gemm` is such a kernel, correct against NumPy at every stage count. With one stage it is always latency-bound and more stages always help or are neutral. But no single set of parameters gives all three bottlenecks in turn, for the reason below. Each of HBM, the TMA engine and the Tensor Core is the limit in one of three scenarios (`tests/test_timing.py`) |
| Every number in the report links to its config source | met: each row of the report's resource and number tables links to the config entries it was derived from, and each entry shows its source, with a URL where one exists. A test checks every link resolves |
| Timing model, B200/B300 configs, Perfetto trace, utilization summary, HTML report | met, with the caveats in this document. The B300 config carries NVIDIA's stated SM count (160), memory size and power, and otherwise B200 values marked as assumed equal; nothing in it was measured on a B300 |

**Why one scenario cannot show all three.** In steady state a pipeline with S
stages takes, per K tile, the largest of: the load time, the multiply time,
and the whole round trip divided by S. The first two are throughput limits and
do not depend on S. Adding stages only shrinks the third. So the limit moves
from "latency" to whichever throughput limit is larger, and stays there; it
cannot pass through the memory limit on the way to the Tensor Core. Which one
is larger depends on the kernel's FLOPs per byte and on how much memory
bandwidth this SM gets.

## The model

Time is in nanoseconds. Each CTA is simulated alone on one SM (`timing/model.py`):

| Resource | Behaviour | From |
| --- | --- | --- |
| issue slots | 4 per SM; warp w uses slot w mod 4; one instruction per clock | `clock_ghz`* |
| SMEM | one wavefront per clock, so bank conflicts cost time | `smem_wavefront_clk`* |
| TMA engine | a fixed latency per copy plus bytes at a fixed rate | `tma_latency_ns`*, `tma_bytes_per_clk`* |
| HBM | this SM's share of the device bandwidth, for bytes of lines no CTA fetched or stored before | `hbm_bandwidth_tb_s` (measured STREAM), `sm_count` |
| L2 | a fixed rate for bytes of lines some CTA of this launch already fetched or stored | `l2_bandwidth_per_sm_gb_s`* |
| Tensor Core | this SM's share of the device FLOP rate, plus a latency per MMA | `tensor_core_tflops_*`, `mma_latency_clk` (both measured) |

\* assumed. Measured values are from Jarmusch and Chandrasekaran,
"Microbenchmarking NVIDIA's Blackwell Architecture"
([arXiv:2512.02189v3](https://arxiv.org/html/2512.02189v3)). The model uses
Table VII's throughput and Table V's FP16 m128n128k16 latency. Applying that
latency to other shapes and TF32 is an assumption. The assumed clock also
scales SMEM/TMEM costs, TMA throughput, and MMA latency.

TMA loads, TMA stores and `cp.async` copies share the L2 record, kept per
128-byte line of global memory. The lines a copy reads or writes are charged
to L2 if an earlier copy left them there and to HBM otherwise, and are in L2
once the copy completes. So a store to lines just loaded, a repeated store,
and a `cp.async` from a warm source are charged to L2, and a load of lines a
store wrote is warm.

`b300.yaml` is a configuration of its own. Three entries are NVIDIA's stated
figures for Blackwell Ultra and differ from B200: `sm_count` (160 against
148), `hbm_capacity_gb` (288 against 192) and `max_power_w` (1,400 against
1,200); the last two are recorded and not used by the model. No other B300
figure is public, so every other entry is the B200 value with the source
"assumption: assumed equal to B200, uncalibrated", starred in the report.
The whole-GPU HBM bandwidth and Tensor Core rates are among them, so with
more SMs one B300 SM's share of each is 148/160 of a B200 SM's.

Each resource is a first-come-first-served server. A warp's instruction starts
when the warp and its issue slot are free. A TMA copy or an MMA queues on its
servers and completes later; warps waiting on its mbarrier resume then. The
timed engine (`timing/engine.py`) always advances whichever warp or completion
is earliest, so cause precedes effect. Functional results and findings are the
same as in an untimed run.

`active_sms` says how many SMs share HBM. The default is all of them, as in a
problem that fills the device. It must be an integer from 1 to the config's
SM count. `warplens.timing.placement.place` gives the number a launch's own
shape implies (grid, cluster size, and how many CTAs of the kernel one SM holds),
assuming CTAs are spread over the SMs; the timing benchmarks' predictions use it
per launch (`validation/blackwell_timing/README.md`, "Active SMs"). A launch
does not use it by itself. Config rates and clocks must be finite and positive; latency costs
must be finite and nonnegative. Invalid configurations raise `LaunchError`
before execution, and unknown override names are rejected.

The roofline's achieved rate is a **pipeline rate**, using mean per-CTA MMA
FLOPs divided by the mean interval containing asynchronous work. It excludes
kernel setup and epilogue time; the report shows the complete kernel time
separately. The compute ceiling follows the MMA kinds actually executed. For
mixed FP16/TF32 work, it divides the total FLOPs by the sum of each kind's
ideal service time at its configured rate. The report records `active_sms`
as a launch assumption instead of presenting it as the config's SM count.

**Verdict.** A resource busy at least 85% of the time is named the bottleneck.
If none is, the kernel is called latency-bound. For the TMA engine, HBM, L2 and
the Tensor Core, "the time" is the interval in which asynchronous work was in
flight; the threshold is a choice, not a derived number. Busy fractions and
the pipeline window are averaged over the CTAs that did work (used shared
memory, a TMA or `cp.async` copy, or the Tensor Core), so CTAs that start and
return do not dilute them; the summary says how many were left out, and
`report.utilization_all_ctas` keeps the average over every CTA. If no CTA did
such work, all are averaged.

## Using it

```python
stats = sim.launch(ptx, "kernel", grid=..., block=..., args=[...], timing=True, active_sms=8)
t = stats.timing
print(t.summary())                 # time, utilization, verdict, roofline
t.write_trace("run.trace.json")    # open at ui.perfetto.dev
t.write_html("run.html")           # self-contained report
```

Pass `timing=GpuConfig.load("B200").replace(tma_bytes_per_clk=512)` to try other
parameters; overrides are labelled as such in the report.

The trace has one process per CTA, a track per warp (run and wait slices, the
wait naming its instruction), tracks for the TMA engine and the Tensor Core,
instants for mbarrier phase completions, and a counter of TMA bytes in flight
from issue through completion, including copies queued for the TMA engine.
Overlapping asynchronous lifetimes use separate display lanes in the trace
and HTML timeline. These lanes do not represent extra engines. They avoid
crossing duration events on one track, which the
[Chrome/Perfetto format does not permit](https://perfetto.dev/docs/getting-started/other-formats).

## `warplens report` and the static views

```
warplens report [-o DIRECTORY] [--no-timing] [options of run] program [arguments...]
```

runs the program as `warplens run` does, with the timing model on, and writes
`DIRECTORY/index.html` (default `warplens_report/`). From Python,
`warplens.viz.write_report(directory, [(name, stats), ...])` writes the same
page for any launches. For each launch the page has:

| View | Module | What it draws | From |
| --- | --- | --- | --- |
| Findings | `check/report.py` | each finding with its PTX line | `stats.findings` |
| Bank heatmap | `viz/smem.py:bank_heatmap_svg` | a row per shared-memory instruction, a column per bank; a cell is the most distinct words one execution put in that bank (1 = conflict-free, N = N-way) | `stats.smem.instructions[...].bank_peak` |
| SMEM layout | `viz/smem.py:layout_svg` | a logical tile beside the 128-byte lines of shared memory it occupies, per 4-byte word, coloured by bank; one picture per shape of TMA tensor copy | `stats.smem.tiles` |
| TMEM map | `viz/tmem.py:accumulator_svg`, `pair_svg` | where the rows and columns of each shape of MMA result land; both CTAs for `cta_group::2` (M = 256, and M = 128, the PTX manual's Layout B) | `stats.smem.mmas` |
| mbarrier timeline | `viz/html_report.py:timeline_svg` | warps, TMA engine and Tensor Core of the first CTA over simulated time, a red line per mbarrier phase completion | `stats.timing` |

Every picture is inline in the page and written beside it as an SVG file; a
timed launch also gets its full timing report (`*.timing.html`, the page
described under "Using it") and its trace (`*.trace.json`), linked from the
page. `python -m warplens.viz.smem` and `python -m warplens.viz.tmem` draw the
two layout views without a run. `docs/guide.md` 6.5, 6.6 and 6.8 show all of
them in use.

What the recording costs: `SmemReport` (`units/smem_banks.py`) keeps
`bank_peak` per instruction and two dictionaries, `tiles` and `mmas`, filled by
one call each in `units/tma.py` and `units/tcgen05.py`. Nothing in the
simulator reads them.

Checked on: `examples/01_smem_transpose` (heatmap: 32 in every bank for the
linear load, 1 for the padded and swizzled ones), `examples/04_pipelined_gemm`
(two 128B-swizzled tiles, a 128 x 64 MMA, the timeline),
`examples/05_triton/run.py` under `warplens report` (launches in a child
process) and CUTLASS tutorial 4 under `warplens report` (multicast TMA tiles
and the 256 x 256 `cta_group::2` MMA). `tests/test_viz_smem.py`,
`tests/test_viz_tmem.py` and `tests/test_viz_report.py` check the structure of
the output, not its appearance.

Not done:

- The SMEM layout view draws tiles placed by TMA tensor copies, or described
  by hand. A layout a kernel computes itself (the transpose example's padded
  and XOR-swizzled tiles) is not recovered from a run, and neither are the
  operands an MMA descriptor addresses or raw `cp.async.bulk` ranges.
- The pictures are static SVG with tooltips; there is no dark theme and no
  interaction. The plan's interactive viewer is later work.
- The timeline shows the first CTA only, as before.
- Launches made through the Python API inside a script are not seen by
  `warplens report`; the script calls `write_report`.
- The plan's CLI also names `warplens check`. It is not built.

## Limits

- Uncalibrated; see the top of this document.
- CTAs do not interact in time. Each starts at zero on its own SM; they share
  only the record of which bytes are already in L2, in launch order.
- No L2 capacity, associativity or eviction: bytes fetched once count as cached.
  Within a CTA, an outstanding fetch does not count as a completed cache fill;
  another load before its completion still pays the cold-fetch cost. In-flight
  requests are not merged. A TMA store to lines L2 does not hold is charged
  to HBM, as if written through; the later write-back of lines a store found
  in L2 is not charged to anything.
- A warp is charged a fixed wait for a global load and nothing for a store.
  An `atom` is charged as the load and then the store it stands for: two
  issue slots, and the wait of a global load or, in shared memory, its
  wavefronts twice. That is an assumption; nothing was measured.
  Ordinary loads and stores neither consult nor update the L2 record.
- The Tensor Core does not model the dependency of an accumulating MMA on the
  one before it, beyond queueing them.
- TMEM loads and stores have a fixed cost (`tmem_access_clk`). `tcgen05.wait`
  costs only the issue clock every instruction costs.
- The roofline's memory ceiling counts every byte as coming from HBM.
- What `warplens report` and the static views leave out is listed in the
  section above.
- Configs live in `warplens/configs/`, inside the package, not in a top-level
  `configs/` directory as the plan sketched, so that they install with it.
