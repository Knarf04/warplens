# Validation matrix

Every claim the simulator makes about Blackwell behaviour that has not been
checked on Blackwell hardware, and how one scripted run on a rented B200 will
test it. This is steps B5, B6 and F23 of `PLAN.md` section 11.

**Nothing in this document is a statement about what a B200 does.** The
"predicted output" column is what the simulator does today. The only hardware
results the repository holds are from an RTX 3080 Ti (Ampere), recorded in
`validation/README.md`; rows that rest on them say so and cite the golden file.

## How to read the table

One row per claim, grouped by area. The columns:

| Column | Content |
| --- | --- |
| Id | Stable; never reused. New rows take the next free number in their area |
| Claim | What the simulator does, stated so that a probe can contradict it |
| Code, docs, tests | `file:function` that implements it, the write-up that documents it, a test that pins it |
| Basis | Why the simulator does this today; one tag from the list below, then details |
| Probe | Planned location, then the kernel and its inputs. Locations are `<probe directory>/<short name>`; the files do not exist yet |
| Predicted output | What the simulator produces for that probe, in words or as a formula |
| Pass criterion | **bit-exact**, **tolerance** (stated) or **informational** (no pass or fail), then what a mismatch means for the simulator |

Basis tags:

| Tag | Meaning |
| --- | --- |
| `ampere` | measured on the RTX 3080 Ti; the golden file is cited. Not yet confirmed on Blackwell |
| `cutlass` | read from CUTLASS or CuTe sources or NVIDIA's documentation of them |
| `ptx-manual` | read from the PTX manual: a section the repository cites, or, where the row says "no section is cited", only the plan's general rule that instruction semantics follow the PTX ISA (`PLAN.md` section 7, item 1) |
| `kernel-output` | inferred from a real kernel producing correct output in the simulator |
| `review` | taken from a code review without verification |
| `published` | a number or rule published by a third party or in CUDA's API documentation |
| `assumption` | none of the above |

Conventions used in the probes:

- *(timeout)* marks a probe that may hang on hardware. It runs in its own
  process under a time limit, and "did not finish" is a recorded outcome.
- *Exact pattern* means operands chosen so that every product and every
  partial sum is an integer below 2^24. The result is then the same in any
  order of accumulation, so a bit-exact comparison tests placement and
  addressing without testing rounding.
- A probe prints raw bit patterns, never formatted floats.
- "The simulator refuses" means it raises an error instead of running. Such
  rows are informational: hardware can only show an outcome, not a rule.

## MMA (`MMA-nn`)

Probes in `validation/blackwell/mma/`. The readout trick used below: with B a
one-hot matrix (`B[n, k] = 1` when `k == n`, N = 16 for half precision), the
result is `D[m, n] = A[m, n]`, so the result shows which shared-memory element
the tensor core took for every (row, k). Filling A's buffer with each
element's own index then prints the addressing function. Indices above 2048
are not exact in half precision, so the probe runs twice, with the index
modulo 1024 and the index divided by 1024.

## Discrepancies found

Between documents and code, found while tracing each row. The code is taken
as the claim in every case.

1. *(Resolved: `docs/m2.md` said the largest tensor dimension is 2^31; it now
   says 2^32, as `warplens/host/tensor_map.py:MAX_DIM` does.)* TMA-11 probes
   the limit.
2. *(Resolved: a launch accepted 228 KB of shared memory per CTA while the
   shim reported an opt-in maximum of 227 KB. Both are 227 KB now; RT-04
   still probes it.)*
3. *(Resolved: the Instructions table of `docs/coverage.md` said TMA has "no
   multicast" and tcgen05 has "no `cta_group::2`", and its Clusters table said
   multicast is "not on raw `cp.async.bulk`". Both tables now say what the
   code does: multicast on tensor loads and raw bulk loads, and
   `cta_group::2`.)*
4. *(Resolved: the module docstring of `warplens/units/tcgen05.py` said
   "`cta_group::1` only" and described only K-major operands; it now covers
   `cta_group::2` and MN-major half-precision operands.)*
5. *(Resolved: `docs/numerics.md` marked `min`, `max` and float-to-integer
   conversion as checked on a GPU with no record. They have now been run on
   the RTX 3080 Ti: `validation/ampere/minmax_cvt_golden.txt`, read by
   `tests/test_hardware_golden.py::test_min_max_and_float_to_integer_match_real_gpu`.
   Every conversion matched. `min` / `max` of two NaNs did not, and
   `warplens/units/alu.py:_min_max` was changed to give what the GPU gives.
   NUM-11 is now an `ampere` row.)*
6. *(Resolved: `validation/README.md` had no row for `prmt`; it has one now,
   and `validation/ampere/build.sh` builds the program that records it.)*
7. *(Resolved: `docs/m4.md` said `tcgen05.wait` has a fixed cost; it now says
   only TMEM loads and stores do, as
   `warplens/timing/model.py:Timeline.charge` does.)* TIM-19 states the code's
   behaviour.
8. *(Resolved: `PLAN.md` said two of the book's GEMM kernels run; it now
   says all nine.)*
9. *(Resolved: the "Not implemented" lists of `docs/m2.md` and `docs/m3.md`
   named `.multicast::cluster`, `cta_group::2`, multicast commit and MN-major
   operands. Each list now says which of its entries a later milestone
