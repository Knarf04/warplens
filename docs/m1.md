# M1: shared memory

M1 adds per-CTA shared memory with a bank-conflict model, named barriers,
warp shuffles, a deadlock report, and the first checkers.

```
$ python examples/01_smem_transpose/run.py
== linear: output matches NumPy, 4096 bytes of shared memory per CTA
Shared-memory bank conflicts (32 banks x 4 bytes)
  line  instruction                  execs  wavefronts  ideal  conflicts   worst
    48  st.shared.b32 [%r12], %r7;      64          64     64          0    none
    54  ld.shared.b32 %r17, [%r16];     64        2048     64       1984  32-way
```

## Acceptance

| Criterion | Result |
| --- | --- |
| Transpose in linear / padded / swizzled layouts reports 32-way / none / none | met: `tests/test_smem.py::test_transpose_bank_conflicts` |
| Same counters as `ncu` on a real Ampere GPU | **partly met.** On an RTX 3080 Ti the bank-conflict counters (total, loads, stores) and the shared instruction counts match exactly for all three layouts. The total wavefront counter is 4160 higher on hardware in every layout. A probe showed what that is: hardware also counts two wavefronts per warp and one per CTA per `__syncthreads()`, whatever the kernel does with shared memory. With those added the totals match too. See `validation/README.md` |

Two other things were checked against the real GPU (an RTX 3080 Ti):
`shfl.sync` matches on all 720 recorded cases, and a barrier completes when
some threads have already returned, in the simulator as on hardware.

## Design decisions

**Shared addresses are offsets.** nvcc keeps shared addresses in 32-bit
registers (`mov.b32 %r9, tile`), so a shared address is a byte offset into the
CTA's shared memory. `cvta.shared` maps it into a fixed window of the generic
address space, and a generic `ld`/`st` routes by address. `ld.global` cannot
reach shared memory.

**Layout.** Sized `.shared` variables are placed in declaration order with
their alignment. Dynamic `.extern .shared` arrays share a base aligned to at
least 16 bytes and to the strongest alignment declared by any dynamic alias.
They get the `smem=` bytes passed to `launch`; alignment padding also counts
towards the per-CTA limit of 227 KB
(the maximum per thread block for compute capability 10.x in the CUDA C++
Programming Guide; 228 KB is the amount per SM).

**Bank model** (`units/smem_banks.py`). 32 banks of 4 bytes; the word at byte
offset `o` is in bank `(o // 4) % 32`. For one warp instruction:

- `wavefronts` = the largest number of distinct words in any one bank;
- `ideal` = `ceil(distinct words / 32)`;
- `conflicts` = `wavefronts - ideal`.

Lanes touching the same word do not conflict. `conflicts` agrees exactly with
`ncu` on real hardware for the transpose kernels. The absolute `wavefronts`
and `ideal` numbers do not: on Ampere the hardware counter also includes two
wavefronts per warp and one per CTA per `__syncthreads()`, which are not
shared accesses (`validation/README.md`). `stats.smem.ncu_wavefronts` adds
them, to compare with `ncu`.

**Barriers count warps.** `bar.sync n` blocks the warp until the barrier
completes. With a thread count, it completes when arrived warps x 32 reach
the count. Without one, it completes when every warp of the CTA that has not
finished has arrived. An explicit sync count of zero has the same meaning as
an omitted count. Other counts must be multiples of 32, and `bar.arrive`
requires a nonzero count. Conflicting explicit counts or repeated arrivals
by a warp before phase completion raise an error. `bar.arrive` arrives without
blocking.

**Blocking.** A warp has a `blocked` field; the engine skips blocked warps and
asks the CTA to release and reset completed barriers after every warp
instruction, before another warp can join the next phase. This is the
mechanism M2's mbarrier waits will reuse.

**Deadlock.** If no warp can run and no barrier can complete, the launch stops
with `DeadlockError`, listing each barrier, how many warps arrived, what it
needs, and the PTX line where each warp waits.

**Findings** (`check/report.py`) are problems that do not stop the kernel.
`launch` returns them in `stats.findings`; each names the PTX line and the
first CTA, warp and lanes, and repeats are counted per instruction. Distinct
instructions on the same source line retain separate counters and findings.

| Finding | Meaning |
| --- | --- |
| `smem-race` | two warps touched the same byte, at least one writing, with no barrier that both warps took part in ordering the first access before the second. Atomic updates (`atom`, added later) do not race with each other, only with another warp's ordinary load or store: `units/smem.py` keeps a separate record of the warps whose atoms touched a byte |
| `smem-uninitialized-read` | read of shared memory this CTA never wrote |
| `barrier-in-divergent-code` | an aligned CTA barrier has a divergent guard predicate, or a cluster barrier has partial warp participation |
| `shfl-inactive-source` | a shuffle read a lane that was not executing it or was outside the caller's member mask |
| `shfl-membermask-mismatch` | a caller is absent from its mask, or a live named member is not executing with the same mask |
| `warp-sync-membermask-mismatch` | the same, for `bar.warp.sync` (`__syncwarp()`), which a later milestone added: lanes on separate divergent paths do not wait for each other |

Exited or unlaunched lanes may remain in a shuffle's member mask. Disjoint
groups with different member masks may execute the same instruction together.

The race check does not depend on the schedule. A kernel with a missing
`__syncthreads()` gives the right answer under round-robin scheduling and is
still reported; [scheduling.md](scheduling.md) has schedules under which its
answer changes too.

**What a barrier orders.** Each warp of a cluster has a vector clock
(`core/clocks.py`): for every other warp, how much of that warp's work it is
ordered after. A warp that arrives at a barrier releases what it has done so
far; a warp that waits at the barrier and passes it acquires what the arrivals
released. This holds for `bar.sync` and `bar.arrive` (which releases and
acquires nothing), for an mbarrier (an arrival releases, a successful
non-relaxed wait acquires, `.relaxed` forms do neither) and for the cluster
barrier. So only the warps that took part are ordered: a `bar.sync 1, 64`
between two warps says nothing about a third, and an mbarrier phase completed
by warp 1 and awaited by warp 2 does not order warp 0. Two exceptions are
deliberate. A barrier with no thread count, and the cluster barrier, complete
without the warps that have returned, so what those warps did counts as
before it. And a `tcgen05.commit` arrives on its mbarrier with what its warp
had done when it issued the commit.

Shared memory keeps, per byte, the last ordinary writer and its clock, and the
readers. One writer is enough, since two unordered stores are themselves
reported. Readers do not conflict with each other, so a store must be checked
against all that are not ordered one after another: a byte holds one reader
while each new one is ordered after the last, and a clock per warp from the
moment two unordered warps have read it, until the next store
(`units/smem.py`, `_Accesses`). Atomic updates are recorded the same way.
Before, there was one barrier epoch per CTA that every completion advanced,
and one last reader per byte; `tests/test_smem_ordering_regressions.py` has
the races that this missed.

## Known limits

- The race check works per warp. Two lanes of one warp are never reported
  against each other, and a barrier that only some lanes of a warp reach
  counts for the warp.
- The per-warp reader clocks take 4 bytes per byte of shared memory per warp
  of the cluster, allocated when a CTA first has two unordered readers of a
  byte and touched only for such bytes: at most 29 MB for a CTA of 32 warps
  with all 227 KB read that way, but 16 times that per CTA in a cluster of 16
  such CTAs.
- An access from another CTA of the cluster is recorded, and a local access
  that races with it is reported, but no finding is raised at the remote
  access itself.
- Per-thread barrier semantics in divergent code are not modeled; the warp is
  counted as a whole and the situation is reported.
- Shuffles do not rendezvous lanes executing separate divergent paths. Such
  rendezvous is legal on `sm_70+`, but the current SIMT executor can report
  participation/source findings and does not guarantee those results.
- `bar.red`, `shfl.sync` on anything but `.b32`, and vector loads and stores
  are not implemented.
- The bank report is text only. The per-bank word counts needed for a heatmap
  are collected (`InstrBanks.bank_words`) but not drawn yet.
