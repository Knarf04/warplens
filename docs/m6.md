## `warplens run` for compiled programs

A program built by `nvcc` normally contains machine code for a real GPU and
links the CUDA runtime statically. Two things have to change, both at build
time and neither in the source:

```
nvcc -gencode arch=compute_100a,code=compute_100a --no-compress --cudart shared prog.cu -o prog
```

- `code=compute_100a` embeds PTX instead of machine code; `--no-compress`
  keeps it readable.
- `--cudart shared` links `libcudart.so`, which `warplens run` replaces.

`warplens run prog` starts the program with two small shim libraries
preloaded (`warplens/shim/`, C, built on first use against the installed CUDA
headers). They implement the runtime calls programs make and forward each one
over a socket to the `warplens run` process, which executes it in the
simulator:

| What the program does | What happens |
| --- | --- |
| registers its fat binary and kernels (compiler-generated) | the PTX is extracted and parsed; parameter sizes are read from it |
| `cudaMalloc`, `cudaMemcpy`, `cudaMemset`, `cudaFree` | simulated global memory; freed addresses are never reused |
| `kernel<<<grid, block, smem>>>(args)`, `cudaLaunchKernelExC` | a launch, with the cluster shape if one is given; argument bytes are copied as they are |
| `cudaGetDriverEntryPointByVersion("cuTensorMapEncodeTiled")`, then calling it | a warplens tensor map, validated like the real call |
| `printf` in a kernel | printed by the program, in order with its own output |
| device and function queries | a simulated B200: compute capability 10.0, 148 SMs |

An error in a kernel (a `MemoryFault`, a deadlock, unsupported PTX) is printed
and reaches the program as `cudaErrorLaunchFailure`. At exit `warplens run`
prints one line per kernel launch and any findings. `--timing` adds the
approximate timing model.

For the CUTLASS tutorials this replaces the hand-built arguments of
`examples/03_cutlass_mma/run.py`: CuTe's own host code builds the tensor maps
and launch parameters, and the results are the same.

## Triton

`warplens.triton_driver.install("B200")` makes Triton compile for `sm_100a`
and launch into the simulator. Triton's bundled toolchain does the compiling;
no GPU or CUDA driver is involved. `kernel[grid](...)` then works as usual,
with tensors created by `gpu.tensor(numpy_array)` and `gpu.empty(shape,
dtype)`. `warplens run script.py` installs the driver and runs the script.

Triton's matmul compiles to a `tcgen05.mma` on this target, so it exercises the
same tensor core as the CUTLASS examples by a different code generator. It
needed: MN-major MMA operands, `ldmatrix`, `bfe`, `prmt`, and the older
per-thread `cp.async` with commit and wait groups. Each of the last four was
checked against the RTX 3080 Ti.

Running the matmul under the timing model exposed a real bug:
`cp.async.wait_group N` counted pending groups instead of waiting for all but
the N most recently committed ones. The two agree when copies finish in the
order they were issued, which untimed runs guarantee and timed runs do not.

## CuTe DSL spike

Question from the plan: can `cute.compile` emit PTX without a GPU, and how do
the PTX and launch parameters get out?

- **Yes, it compiles without a GPU.** With `CUTE_DSL_ARCH=sm_100a` and
  `CUDA_VISIBLE_DEVICES=""`, `cute.compile(host, ...)` succeeds
  (`nvidia-cutlass-dsl` 4.8.1).
- **The PTX is available on request.** `CUTE_DSL_KEEP=ptx` writes it to
  `CUTE_DSL_DUMP_DIR`. For a small kernel with `cute.printf` it parsed and ran
  in warplens unchanged (`examples/06_cute_dsl/run.py`).
- **Launch parameters are not extracted.** The compiled host function launches
  through the CUDA driver API, which warplens does not emulate, so the example
  repeats grid, block and arguments by hand. Emulating enough of the driver
  API for the DSL's launch path is the missing piece.
- Not tried: a DSL kernel that uses TMA or tcgen05, and whether the DSL's
  tensor-map construction can be redirected.

The DSL was installed in a separate virtual environment, not in the project
env, and the example has no automated test.

## Limits

- **Build flags are required** for compiled programs. A binary with only
  machine code is reported with the flags to use; it cannot be simulated.
- **The shim covers what the four tutorials call**, about thirty functions.
  A program that calls anything else fails to start with an unresolved symbol,
  or silently reaches the real runtime if that is installed: only the listed
  functions are replaced. Streams, events, multiple devices, unified memory,
  textures and `cudaMemcpy2D` are not there.
- Everything is synchronous and single-device. `cudaFree` does not release
  memory.
- The shim libraries are Linux-only and are compiled on first use; that needs
  a C compiler and the CUDA headers.
- Triton: no torch tensors, no benchmarking interface, no kernels that need a
  global scratch buffer. Only what the two example kernels exercise has run.
- CuTe DSL: see above.
