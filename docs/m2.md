# M2: TMA and mbarrier

M2 adds asynchronous bulk copies between global and shared memory (TMA), the
tensor maps that describe them, mbarriers, proxy fences, and checkers for the
ways this protocol is usually broken.

```
$ python examples/02_tma_copy/run.py
Round trip GMEM -> SMEM -> GMEM for each swizzle mode:
  swizzle  None, box (16, 32): correct, 0 finding(s)
  swizzle   32B, box (16, 8): correct, 0 finding(s)
  swizzle   64B, box (16, 16): correct, 0 finding(s)
  swizzle  128B, box (16, 32): correct, 0 finding(s)

== bug 1: expect_tx too small
deadlock in CTA (0, 0, 0): every unfinished warp is blocked and nothing can release them
  ... 1024 completion byte(s) have not been accounted for by expect_tx (expect_tx too small or missing?)
```

## Acceptance

| Criterion | Result |
| --- | --- |
| A TMA copy kernel round-trips GMEM -> SMEM -> GMEM for every swizzle mode | met: `tests/test_tma.py::test_round_trip_for_every_swizzle_mode` |
| Wrong `expect_tx` is caught | met for the example kernel, both ways. Too large: the wait raises `DeadlockError` naming the bytes still expected. Too small: one 2048-byte copy completes against a 1024-byte expectation, the count stays at -1024, and the wait deadlocks in warplens's PTX model; the error also carries an `mbarrier-tx-mismatch` finding in `DeadlockError.findings`. Returning with unmatched completion bytes gives the same finding without a deadlock |
| Missing fence is caught | met: `tma-store-missing-fence` |
| Early reuse is caught | met: `tma-store-source-overwritten`; a skipped mbarrier wait gives `tma-load-unsynchronized` |

The example kernel is CUDA C++ with the same inline PTX that CUTLASS uses for
these operations, compiled by nvcc for `sm_100a`; `ptxas` accepts it.

**Nothing in M2 has been compared with hardware.** The development GPU is
Ampere, which has no TMA. The semantics here come from the CUDA 13.5 headers,
the CUTLASS sources and the plan's design notes. The points most worth
confirming on a real Hopper or Blackwell GPU are listed under *Assumptions*.

## Design decisions

**Tensor maps are warplens's own encoding.** A real `CUtensorMap` is 128
opaque bytes written by the driver. `Device.tensor_map_tiled` plays the role
of `cuTensorMapEncodeTiled`, applies the same documented argument checks, and
writes a 128-byte record that the TMA unit decodes (`host/tensor_map.py`). The
kernel receives a pointer to it in global memory. `box` is given in the
array's NumPy axis order; TMA coordinates inside the kernel are innermost
first. Dimensions, box sizes and element strides must be integers; the maximum
tensor dimension is 2^32, following CUDA 13.5. Decoding validates descriptor
fields again so corrupted maps produce a source-located error.

**A TMA instruction issues a copy; the copy completes later.** Completion is an
event `async_delay` scheduling rounds after issue (default 4), or immediately
if no warp can run. A load reads global memory when issued and writes shared
memory when it completes, then performs `complete_tx` on its mbarrier. A store
reads shared memory when it completes. `async_delay` must be a nonnegative
integer. Copy bounds are checked before allocating transfer-sized temporary
arrays, and tensor coordinates must preserve 16-byte alignment of the box.

**mbarrier.** Each mbarrier tracks pending arrivals and expected bytes for its
current phase; the phase completes when both are zero. Every lane that executes
an `arrive` arrives. `try_wait` blocks the warp until the phase completes
instead of returning false, so a wait that can never succeed becomes a
deadlock report. `test_wait` never blocks. The model encodes an arrival token
with its phase parity in bit 63 and the low 32 bits of the phase number below.
A state wait's predicate compares bit 63 with the barrier's current parity;
the `.parity` forms compare bit 0 of their operand. This reproduces the recorded
RTX 3080 Ti predicates (`validation/ampere/mbarrier_token_golden.txt`), including
exploratory stale and made-up inputs. `try_wait` needs `sm_90` and was not
measured. The model's low token bits are for diagnostics; hardware token bits
are opaque and differ. Transaction counts are signed:
completion bytes can precede `expect_tx`, but a phase cannot complete until
the count balances to exactly zero. Generic-address forms accept pointers
produced by `cvta.shared`.

A state token from `arrive` is valid only in its own phase or the immediately
following phase, per [PTX `mbarrier.test_wait` / `try_wait`](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-mbarrier-test-wait-mbarrier-try-wait).
Older or malformed tokens trigger `mbarrier-invalid-token` and grant no
synchronization credit, even when the parity fallback returns true. Invalid
`try_wait` calls do not block on an unrelated phase. Their predicate retains
the measured Ampere fallback solely so exploratory kernels can continue; it
is not a portable result for invalid use or a Blackwell prediction. The model
checks its encoded current and previous phase tokens, but cannot distinguish
a token from another barrier or a reinitialization with the same phase number.
Parity waits cannot distinguish phases separated by an even number of
completions; callers must track their lifetime.

**Bulk groups belong to each issuing thread.** A commit includes that thread's
uncommitted stores, including an empty group if there were none. A wait with
count N orders all but its N newest groups, regardless of which copies happen
to have completed. Another lane's commit or wait cannot complete that protocol.

**Checks do not depend on timing.** Shared memory records, per byte, the TMA
load that last targeted it and the TMA store that last read it. Each warp keeps
the set of copies it has synchronized with: by a successful mbarrier wait, by
`wait_group`, or by meeting another warp at a barrier or mbarrier that already
had. Touching bytes of a copy outside that set is reported, even when the data
happened to arrive in time. The tests run the broken kernels with delays of 0,
4 and 1000 rounds and get the finding each time.

Barrier arrivals publish a snapshot of the copies already synchronized with
at arrival. An mbarrier acquire wait observes its completed phase, not copies
contributed to the next unfinished phase. Explicit `.relaxed` arrivals and
waits do not transfer that synchronization knowledge.

**Fences.** An ordinary store marks its bytes as not yet visible to TMA.
`fence.proxy.async` clears the mark for the warp's own writes and for writes
that a completed barrier already ordered before it. A TMA store of marked bytes
is reported. Its `.global` form does not fence shared memory. Supported
ordering fences and `fence.proxy.alias` have no additional modeled effect;
unsupported proxy modes raise `UnsupportedError`.

**Inline assembly.** nvcc passes `asm` blocks through, including `{ ... }`
blocks with their own `.reg` declarations and labels (the mbarrier wait loop).
Shared variables in those blocks are also scoped, so a nested declaration
cannot overwrite an enclosing variable. Names declared in a nested block are
stored as `name@scope`.

## Findings added

| Finding | Meaning |
| --- | --- |
| `mbarrier-tx-mismatch` | the kernel returned with completion bytes not balanced by `expect_tx`; a temporary negative count is valid |
| `mbarrier-over-arrival` | more arrivals than the phase needed; the surplus completes as many following phases as it covers |
| `mbarrier-invalid-token` | state token is outside the current or immediately preceding phase; its nonportable predicate grants no synchronization |
| `mbarrier-init-race` | an mbarrier used by another warp with no barrier since its `init` |
| `tma-load-unsynchronized` | ordinary read or write, TMA store, or overlapping TMA load touches bytes a TMA load writes without waiting on its mbarrier |
| `tma-store-missing-fence` | TMA store of bytes written by ordinary stores with no `fence.proxy.async` |
| `tma-store-source-overwritten` | ordinary store or TMA load overwrites bytes a TMA store reads, before waiting for it |
| `tma-store-not-waited`, `tma-load-not-waited` | the kernel returned with the copy still in flight |
| `tma-swizzle-misaligned` | a swizzled buffer not aligned to the swizzle period |

TMA stores also report `smem-uninitialized-read` when their source contains
bytes that neither an ordinary store nor a TMA load has written.

Use of an mbarrier before `mbarrier.init`, a TMA instruction whose rank differs
from its tensor map's, and a pointer that is not a tensor map are errors.

## Assumptions to confirm on hardware

- **An undersized `expect_tx` is not always a deadlock.** The PTX specification
  defines a signed transaction count and completes a phase only when pending
  arrivals and that count are both zero, which is what warplens models. With
  one copy and no later `expect_tx`, the count never returns to zero. With
  several copies, an intermediate completion can bring it to zero and advance
  the phase early, and a later `expect_tx` can balance a temporary negative
  count. What hardware does with such a malformed protocol has not been
  measured.

- **Swizzle is a function of the shared-memory address**, not of the offset
  into the buffer: CuTe's `Swizzle<B,4,3>` with B = 1, 2, 3 for 32B, 64B, 128B,
  applied to the address. The two views agree when the buffer is aligned to the
  swizzle period (256, 512, 1024 bytes), which is why misalignment is reported.
- **`complete_tx` counts the whole box**, including out-of-bounds elements that
  were filled rather than read.
- **The NaN used for out-of-bounds fill** is NumPy's default quiet NaN; the
  hardware constant is not documented.
- **Fence scope**: that a fence after a barrier covers other warps' earlier
  writes.

## Not implemented

`.multicast::cluster` and cluster-wide shared memory were on this list at M2;
M5 added them (`coverage.md`, Clusters).

- im2col mode, interleaved layouts, `cp.reduce.async.bulk`,
  `tensormap.replace`.
- `mbarrier.arrive_drop`, `.noComplete`, `mbarrier.pending_count`.
- The ABA check from the plan (waiting on a parity two phases behind).
- Synchronization knowledge and the shared-memory race check are per warp, not
  per thread (the race check orders only the warps that took part in a
  barrier: [m1.md](m1.md)). Bulk-group ownership is per thread, but a successful wait
  still makes its copy visible to the whole simulated warp; divergent
  per-thread synchronization is not fully modeled.
- The L2 promotion and cache-hint settings are accepted and ignored.
